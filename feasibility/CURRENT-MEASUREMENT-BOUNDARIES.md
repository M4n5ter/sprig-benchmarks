# Current-release paired measurement contract (24 October 2026)

This is a new series, not a continuation of prototype performance figures. Sprig main commit fba02ad27a9d82d225d852987a6fd234fe06f122 is built locked/release with the optional projection feature. The same real binary provides default native, explicit projected and owned writable backends. No source patch, private prototype API or direct library shortcut is used. The primary comparator is current released LayerFS v1.1.0, 9f97a7ec95b662e9cb288704afa165feff132cfa. Current upstream main 4497b0cbf6d2c142d7d5caee310b14fb577dd642 adds plugin listings beyond that release. Prior v1.0.0 results remain historical and are not substituted for this comparison.

## Unchanged workload and isolation

The original seven fixtures and 100-step recipes, checksums, write shell, fixed mtimes, order alternation and three repeats remain unchanged. Each backend is a separate paired series with its own contemporaneous comparator samples; results cannot be pooled or compared across runners as causal improvements. A smoke run covers identical and distributed history once before full execution. Each sample uses a fresh temporary 2 GiB Btrfs image with Data SINGLE, Metadata DUP, no compression, noatime. Sources are external and cannot share uncharged extents. No real disks, host security changes, forced or lazy unmounts are introduced.

## Matching logical lifecycle

Both products retain three live workspaces: imported main, first fork work, second fork second. Sprig import creates its main workspace as part of the product operation. Comparator LayerFS.init plus explicit sandbox.create, branch.fork(import-main, main) and workspace.mount(sandbox, import-main) are timed together (main is an immutable project reference, not itself a mountable branch) to match that logical state. The additional main mount is an explicit difference from prior prototype series, where import did not create a mounted workspace. Both branch from unchanged main, read work fully, create and read second fully, then mutate/checkpoint work. Main and second must remain unchanged.

Native Sprig uses actual filesystem workspaces; projection uses the production-managed FUSE/Overlay lifecycle. Owned writable uses its actual journaled CAS/FUSE backend, not an emulation of OverlayFS. Its initial mounts and per-checkpoint normal unmount/publication/remount are charged, and its current path/generation must be reacquired as part of the measured operation. Its exact change journal and busy-mapping rules are disclosed, not credited as equivalent to a native scan with live writers. CLI outputs provide paths. The harness does not emulate a free metadata fork: native copy/reflink traversal and projected source capture, detached-base publication, observation, mount/readiness and synchronization are charged exactly as implemented. Metadata-only branch API is available in production but the separate probe is omitted on both sides to preserve the timed task sequence.

## Time

Initialization is timed separately and included in the preparation headline. Preparation equals init + import + first fork + full checksum read, not total software setup. Warm means second fork + full checksum read. No verified cold-cache claim: metadata validation is charged, no cache dropping is performed, and separate projection processes have independent user-space caches.

The frozen positional dd + fsync + touch write command is unchanged. The fsync precedes restored mtime and does not alone guarantee final metadata durability. Checkpoint means the complete production CLI call, including process startup, locking/leases, capture, object validation, immutable revisions, upper synchronization, state and backups, against the comparator persistent SDK and its configured Disposable global-store WAL/synchronous=OFF plus workspace-overlay MEMORY/synchronous=OFF/EXCLUSIVE. The Sprig harness also writes lifecycle instrumentation inside CLI timers; this overhead remains charged, not subtracted. Checkpoint is the sum of its CLI call and owned-view authoritative show/readiness phase; immediate external acknowledgment-ledger I/O between those phases is excluded just like final per-step ledger writes. All product unmount/remount and publication work remains charged. This is not equal-durability or pure API timing. Unsupported prototype phase counters must not be fabricated or inferred.

## Whole-footprint accounting

Primary storage is Btrfs filesystem Used including Data, Metadata and System, after sync outside operation timers and while main/work/second and all required servers remain live. All Sprig native trees, projection generations or owned writable journals/retained generations, objects, revisions, staging, state, backups, locks and server logs are inside the image. Do not omit retained data because it looks redundant. Comparator image/software, Docker/containerd persistent roots, writable overlays, volumes, SDK home and logs remain inside its fresh image. Runtime-ready subtraction is a diagnostic deployment increment, not exact app-data-only usage. Executable/build inputs and volatile host/RAM state are excluded on both sides. No equal total memory or background-compute claim: the comparator uses one explicit Sandbox/daemon for its three views, while Sprig projection/writable use one server per mounted view.

## Correctness and cleanup

Require all expected records, successful committed responses, 100 distinct acknowledged history IDs, complete reachable history and every historical snapshot's listed-file checksum readback. Historical restore/mount/read verification happens after active footprint sampling; retained data generated by those restores is excluded from the earlier sampled footprint. This series additionally reports aggregate restore-to-usable-workspace, full-read and normal-unmount phase times for all 100 snapshots, separately from checkpoint and preparation totals. Comparator restore includes public branch fork plus mount; Sprig uses public restore plus required mount. These are defined end-to-end API tasks, not free metadata-only restore. Native ordinary-directory cleanup has no unmount operation and reports zero/not-applicable, not equivalent work to filesystem teardown. Verify unchanged source/main/second and exact successful normal cleanup. CLI no-op is not accepted as a distinct mutation. All per-step raw records survive outside the measured image; runtime logs remain charged inside it.

The existing production integration suite is the functional gate; the old adapter-only 11-case oracle cannot be claimed to run unmodified through a different CLI. The new sample verifies the same frozen content/history workload, not a complete mode/mtime/namespace oracle. Native, projection and writable results must be labeled separately. LayerFS v1.1 init removes its sealed temporary Store after installation; any leftover reported by client.created remains counted. Sandbox close follows workspace unmounts and precedes client close. No forced container deletion is used as cleanup fallback. Platform CI establishes bounded functionality, not complete feature parity or a performance win.

## Additional Cargo work

A real dependency-free Cargo clean/no-op/edit/checkpoint/restore/rebuild scenario is a separate integration series, not part of these seven frozen recipes. Its compiler/runtime/image inputs, output execution checks, build artifacts and hardlinks must be matched and disclosed before any timing claim. The owned writable kernel gate already runs small Cargo capability checks inside Sprig, as the production CI does; these gate results are not a matched Cargo performance comparison and must not be reported as one.
