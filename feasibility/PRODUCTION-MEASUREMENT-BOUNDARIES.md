# Production CLI measurement contract

This is a new series, not a continuation of prototype performance figures. Sprig production commit 46f96341498ef040280720d8f97c17de82db4419 is built locked/release with the optional projection feature. The same real binary provides default native and explicit projected backends. No source patch, private prototype API or direct library shortcut is used. The comparator remains the fixed v1.0.0 SHA 2aaf2552ce21154928b9f9c83582e41a637f5910, not current upstream main.

## Unchanged workload and isolation

The original seven fixtures and 100-step recipes, checksums, write shell, fixed mtimes, order alternation and three repeats remain unchanged. Each backend is a separate paired series with its own contemporaneous comparator samples; results cannot be pooled or compared across runners as causal improvements. A smoke run covers identical and distributed history once before full execution. Each sample uses a fresh temporary 2 GiB Btrfs image with Data SINGLE, Metadata DUP, no compression, noatime. Sources are external and cannot share uncharged extents. No real disks, host security changes, forced or lazy unmounts are introduced.

## Matching logical lifecycle

Both products retain three live workspaces: imported main, first fork work, second fork second. Sprig import creates its main workspace as part of the product operation. Comparator project.init plus main workspace.mount are timed together to match that logical state. The additional main mount is an explicit difference from prior prototype series, where import did not create a mounted workspace. Both branch from unchanged main, read work fully, create and read second fully, then mutate/checkpoint work. Main and second must remain unchanged.

Native Sprig uses actual filesystem workspaces; projection uses the production-managed FUSE/Overlay lifecycle. CLI outputs provide paths. The harness does not emulate a free metadata fork: native copy/reflink traversal and projected source capture, detached-base publication, observation, mount/readiness and synchronization are charged exactly as implemented. Metadata-only branch API is available in production but the separate probe is omitted on both sides to preserve the timed task sequence.

## Time

Initialization is timed separately and included in the preparation headline. Preparation equals init + import + first fork + full checksum read, not total software setup. Warm means second fork + full checksum read. No verified cold-cache claim: metadata validation is charged, no cache dropping is performed, and separate projection processes have independent user-space caches.

The frozen positional dd + fsync + touch write command is unchanged. The fsync precedes restored mtime and does not alone guarantee final metadata durability. Checkpoint means the complete production CLI call, including process startup, locking/leases, capture, object validation, immutable revisions, upper synchronization, state and backups, against the comparator persistent SDK and its configured Disposable global-store WAL/synchronous=OFF plus workspace-overlay MEMORY/synchronous=OFF/EXCLUSIVE. The Sprig harness also writes lifecycle instrumentation inside CLI timers; this overhead remains charged, not subtracted. This is not equal-durability or pure API timing. Unsupported prototype phase counters must not be fabricated or inferred.

## Whole-footprint accounting

Primary storage is Btrfs filesystem Used including Data, Metadata and System, after sync outside operation timers and while main/work/second and all required servers remain live. All Sprig native trees or projection generations, objects, revisions, staging, state, backups, locks and server logs are inside the image. Do not omit retained data because it looks redundant. Comparator image/software, Docker/containerd persistent roots, writable overlays, volumes, SDK home and logs remain inside its fresh image. Runtime-ready subtraction is a diagnostic deployment increment, not exact app-data-only usage. Executable/build inputs and volatile host/RAM state are excluded on both sides. No equal total memory or background-compute claim.

## Correctness and cleanup

Require all expected records, successful committed responses, 100 distinct acknowledged history IDs, complete reachable history and every historical snapshot's listed-file checksum readback. Historical restore/mount/read verification happens after active footprint sampling; all costs and retained data generated by those independent oracles are excluded from the sampled workload. Verify unchanged source/main/second and exact successful normal cleanup. CLI no-op is not accepted as a distinct mutation. All per-step raw records survive outside the measured image; runtime logs remain charged inside it.

The existing production integration suite is the functional gate; the old adapter-only 11-case oracle cannot be claimed to run unmodified through a different CLI. The new sample verifies the same frozen content/history workload, not a complete mode/mtime/namespace oracle. Native and projection results must be labeled separately. Platform CI establishes bounded functionality, not complete feature parity or a performance win.
