# Same-runner production synchronization A/B measurement contract

Purpose: decide whether topic 17130154 is worth merging, without inferring causality from separate machines. Baseline 46f9634 and candidate 17130154 remain unmodified. No comparator or new architecture is required for this attribution experiment.

One temporary Ubuntu runner builds both locked release binaries with projection enabled using the same toolchain. Verify source and binary hashes and run each product's existing kernel lifecycle gate. Measure sequentially, never concurrently. The same runner handles native and projection, each with five fixed pairs of A/B samples. Alternate AB/BA order by pair and counterbalance backend order. Keep CPU/environment metadata and every sample, no outlier deletion.

Cases: the three frozen history-distributed/hotset/recurring fixtures, unchanged 100 writes and 100 historical full-byte readbacks; plus a clearly separate small-tree control with eight shallow ordinary files (fewer than 16 observed entries), deterministic bytes/modes/mtime. The control should also do 100 alternating fixed-size edits and historical readbacks, not merely measure a no-op. Its oracle/steps use the existing schema, and its new fixture is labeled a control, not one of the original seven recipes.

Reuse production_sample operation body unchanged. The only required driver adaptation is truthful SHA provenance per selected binary, supplied by a fixed allowlist in the A/B harness, rather than one hardcoded candidate SHA. No change to timing, copying, hashing, validation, synchronization, publication, backend lifecycle, three live workspaces or post-accounting historical restore order.

Each sample gets a new identical 2 GiB Btrfs image with Data SINGLE/Metadata DUP/no compression/noatime. Fixture and step ledger are outside the measured image. Account whole-FS physical Data+Metadata+System while three views and required processes remain live. Preserve normal unmount-only behavior. No Docker or container runtime configuration is needed for Sprig-only A/B. Do not mount on the cloud host or user computer.

Record init/import/fork/fullread/warm/write/checkpoint and total preparation. Report five per-pair ratios and differences, their medians/ranges and raw samples. Do not subtract CLI or sync overhead. Old/new within-run paired comparisons are primary; existing external comparator results remain separate. No claimed cold cache or statistical certainty from only five fixed pairs.

Cost and fixed design: 2 backends x 4 cases x 5 pairs x 2 revisions = 80 samples, 8,000 commits and 8,000 historical readbacks. Choose five pairs before execution, not adaptively after seeing results. Actual previous lifecycle logs give roughly 17–29 seconds per projected history sample and 39–51 seconds native, including restores and cleanup. Using the observed maxima for all 40 samples per backend gives about 54 minutes of workload; propose a 90-minute timeout with two builds/gates and variance margin, build jobs capped at 2. Seven pairs would need roughly 74 minutes of workload before builds, so the initial 75-minute estimate was insufficient.

The 80 sparse images have 160 GiB logical capacity, greater than the previously observed 86 GiB free. Do not assume sparse allocation guarantees completion. Record post-build free space, image allocated bytes and free space before each whole A/B pair. Require at least both fresh 2 GiB image capacities plus an 8 GiB host reserve before starting a pair. Stop as incomplete if the guard fails; never trim historical oracles or discard raw to make a partial run look complete. After the entire pair succeeds, raw and all history readback/oracle outputs are persisted, and ordinary unmount succeeds, remove only the two specifically recorded harness-created image files. Before unlink, verify each exact resolved path is under its dedicated mkdtemp directory inside RUNNER_TEMP, it remains a non-symlink regular file, no mountinfo entry refers to its mountpoint, and losetup reports no loop device attached to that image. Use exact file unlink, not recursive rm or wildcard cleanup. If any check or sample fails, preserve its image and diagnostics and fail; never force/lazy unmount. Record cleanup success after each pair. Keep the capacity guard and record actual allocated bytes before removal. Always normally unmount before leaving a sample. The fixed cost/design was approved before implementation; no adaptive pair-count changes are allowed.

Control guard: eight files directly in source root, root plus files exactly nine manifest entries; no generated temporary logical files. This verifies observed <16 so both candidate backends use the unchanged serial synchronization path. All 100 edits must change bytes and produce distinct revisions.

The standalone workflow implements this bounded experiment. Publication requires the integration review; successful execution is established only by complete raw records, not by this plan. Existing production code and earlier reports/raw remain unchanged.

Primary endpoints are each 100-step write + checkpoint total and checkpoint-only total. Preparation and warm fork/read remain reported secondary endpoints, with physical storage retained as a no-format-change check. Each per-pair ratio is candidate/baseline (less than one is faster); report all five ratios, median and range without treating five pairs as high-confidence statistical proof.
