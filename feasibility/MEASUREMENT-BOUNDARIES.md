# Independent Btrfs prototype series: frozen measurement boundaries

This is a feasibility experiment, not production Sprig or feature parity. Run tiny paired smoke before the existing seven-case, three-repetition series. Original ext4 scripts and raw results remain unchanged.

## Operations, timing, and correctness

- Software installation/build, runtime restart, fixed image loading, fixture generation, and empty-filesystem creation are outside operation timers. Record versions, image identity, script hashes, and machine information. No cross-run causal speedup claim.
- Native initialization is separately timed. LayerFS initialization includes volume creation, SDK home, and SDK constructor; project.init then includes product store initialization. Report both the defined import + fork + read phase sum and init-inclusive phase sum. Neither is complete machine startup or software deployment wall time. Metadata probe is separately reported, not silently included in a phase sum.
- Each sample gets a new Btrfs filesystem and fresh product store. There is no drop_caches: “first” means first workspace read in that lifecycle, not proven cold RAM/device cache. The second fork/read is warmed by the preceding work. Product order alternates across repetitions; fixture and software caches may persist across samples.
- Both full-read tasks use identical coreutils sha256sum checks over all fixture files. Native uses a host shell subprocess; LayerFS uses Docker workspace.exec. Native snapshot/dedup operations are Python in-process, LayerFS calls are SDK in-process. Transport/process overhead is part of practical interfaces, not a kernel-only comparison.
- Same imported data, metadata-only probe, work branch, second unchanged branch, and 100 acknowledged distinct history commits where applicable. Source is outside the measured filesystem and cannot donate uncharged shared extents. Native additionally retains an imported native main tree because that is its representation; no artificial main mount is added to LayerFS.
- Same inode-preserving dd write command, byte ranges and fsync, followed by touch restoring mtime. touch occurs after fsync, so write time does not certify durable final mtime. Native publication uses fsync/synchronous snapshots; LayerFS uses its Disposable configuration and synchronous OFF, with overlay MEMORY journaling. Do not call durability equivalent.
- No extra single-product scan between timed first and second reads. Accounting and independent historical oracles happen after timed operations. Native's built-in safety/oracle checks after its timed phases remain included in process wall time only, not the phase sums.
- Require final bytes, all 100 distinct acknowledged commit identities in history, and full checksum readback of every historical snapshot after timing. Verify unchanged retained second workspace. These are byte/history oracles, not an exhaustive mode/mtime/extra-path oracle. Additional LayerFS validation branches are created only after the storage sample and excluded as test machinery.
- Snapshot import/fork/history correctness does not establish merge, stale-writer resolution, recovery, reopen, SDK, GC, or security completeness for the native prototype. Its RAM-only dedup index has no reopen/rebuild path. The 4 KiB insertion recipe cannot establish arbitrary-offset CDC performance.

## Storage boundary and lifecycle

- Both use fresh 2 GiB regular loop images, data SINGLE, metadata DUP, no compression, noatime. Filesystem Used is measured after btrfs filesystem sync outside timers. It counts shared data once and includes metadata/system profile overhead. Allocated chunk capacity and GlobalReserve are not added as used bytes.
- Native includes every snapshot/workspace, metadata DAG, and file in its filesystem. Its Python process has exited when sampled: trees remain, but its RAM index does not. LayerFS is sampled with work and second workspaces mounted and SDK/container alive. This is a retained-filesystem comparison, not matched live-control-service or RAM lifecycle.
- LayerFS filesystem contains Docker data-root, containerd persistent root, ordinary local volume, SDK home, active overlay databases, writable container layers, engine metadata, and container logs. This includes store.sqlite and sidecars, retained sealed.sqlite, SDK discovery records, uploaded daemon binary/setup, and overlay databases under /layerfs-local. Secret record/config contents are never published.
- Record empty-filesystem usage and LayerFS runtime-ready usage after loading the fixed base image but before product creation. Final minus empty is whole experimental deployment growth; final minus runtime-ready is incremental growth, including product-triggered runtime metadata and uploaded software. Neither is exact application-data-only space. Do not claim a storage win merely by charging an OS image or daemon binary to one product.
- Raw btrfs filesystem usage/df/du reports and Docker graph-driver/log paths are retained. Recursive du alone is not authoritative physical usage and component totals are not summed across shared extents. No invented exclusive-byte subtraction.
- Persistent containerd root is relocated too. Volatile /run state, host system journal, shared installed executables, and source fixture are outside the filesystem metric; they are software/host baseline, not claimed absent. Container logs inside Docker root are included. Host journal growth is not measured, so “all machine disk consumption” is not claimed.
- Native reports estimated index RAM and peak process RSS. LayerFS RAM and background compute are not comparably profiled in this experiment. No memory-efficiency or total CPU claim. Background daemon work may overlap SDK timings and final accounting sync.

## Runtime isolation, cleanup, and acceptance

- Only on an ephemeral GitHub runner. Reject any pre-existing container before relocating the existing daemon. Change only Docker data-root/storage-driver/containerd-snapshotter and containerd persistent root, preserving socket, state, network, TLS, access settings, and all other configuration. Plain local volumes use the supported path; no target validation patches or bind-volume workaround.
- Back up original configuration outside the image, restore it after each LayerFS sample, and never delete old runtime roots. Remove only this sample's containers/volume after accounting. Unmount normal loop filesystem; cleanup failure makes the record unsuccessful. No host/user real disk is formatted.
- Results report expected case/product/repetition count and mark complete only after every required successful record. Failed/partial runs are diagnostic, not comparative victories. Preserve original raw artifacts. Tiny smoke has one repetition and is not a performance conclusion; full series reports medians with raw samples.
