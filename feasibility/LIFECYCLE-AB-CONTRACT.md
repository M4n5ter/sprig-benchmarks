# Production lifecycle same-runner A/B

This is a separate within-Sprig attribution experiment, not new LayerFS results. Baseline `bc4165f5f55ceac63e18716ac96b19d9e4675afd` and candidate `a2b76e4c3ecdccdeeca24a669df4a82d1a4792f3` use fresh default-auto stores and the same compiler/profile on each runner. Neither production tree is patched. Prior results remain unchanged.

Each job chooses one backend: native, projection, or writable. Smoke has identical and history-distributed with one adjacent A/B pair (4 samples, 200 historical readbacks). Full has the seven frozen cases and five adjacent AB/BA pairs (70 samples, 3,000 historical readbacks). The three backend jobs run serially; across-backend absolute differences are not same-machine evidence. Each pair alternates its ordering according to pair/case index. Cache dropping is not performed, so neither side is described as cold-cache.

Both revisions build into different absolute CARGO_TARGET_DIR paths. Only registry/git downloads may be cached/shared. Source commit, source-file hashes, release binary hash, compiler and build profile are recorded and checked before sampling. All real production startup, capture, synchronization, revision/state publication, owned generation replacement and mount/readiness remain in the existing operation timers.

The sample uses the frozen fixtures and write commands, three active workspaces, 100 distinct acknowledged commits and every historical snapshot readback. No retention pruning, GC, content cache deletion or weakened durability is allowed. Metadata-only probes remain omitted. No-op commits cannot substitute for the required mutations.

Primary storage sampling remains before historical restores, with all three original views live. A new separately named postHistorySpace sample measures cumulative retained state after all historical restore/read/normal-unmount tasks but before final cleanup. The native restored trees remain retained exactly as in the earlier protocol. These two points have different lifecycles and must not be conflated. Component diagnostics run only after all timed operations and the second whole-filesystem sample. Apparent and stat-allocated component sums are not unique physical extent accounting; shared extents/hardlinks may overlap, and mounted FUSE views are never recursively traversed for this diagnostic. Whole Btrfs Used minus empty-FS Used is authoritative for total persistent footprint.

The outer driver reuses the reviewed production A/B temporary-image lifecycle: new 2 GiB sparse image, Btrfs Data SINGLE/Metadata DUP, ordinary mount/unmount, and exact path/inode plus detached-loop verification before deleting only its own verified completed pair images. Failure preserves images and diagnostics; no force/lazy unmount, signals, permission changes or unknown-data deletion are introduced. Runtime logs stay inside the measured image; harness ledgers stay outside. An always-upload artifact preserves failed or partial evidence. Incomplete output must never summarize as a successful experiment.

Summary reports paired candidate/baseline ratios, medians and ranges for initialization-inclusive preparation, warm fork/read, write/checkpoint, individual restore/read/cleanup and restore sum, plus both physical storage points. Zero baseline values (e.g. native unmount time or nonhistory operations) yield null ratios, not invented speedups. Five pairs are directional evidence, not proof of universal statistical superiority.

Cargo transport changes are deliberately excluded from this package. A separate revised Cargo series must charge per-generation compiler-container lifecycle and preserve complete target/cache metadata and real Fresh checks; it cannot overwrite the earlier per-command-container series.
